Deployment story

Swift Lending OS as a lending domain on EDX

Where an institution already runs an enterprise platform, Swift Lending OS deploys as its lending domain — consuming identity, documents, notifications, task management and integration rather than duplicating them.

The pattern

A lending domain on an enterprise foundation

EDX is an enterprise platform organised in layers — a foundation providing runtime and shared services, with business domains built on top, products built on domains, and per-client solutions built on products.

Swift Lending OS is the financial services domain in that model — the lending capability an institution assembles its credit products from.

The benefit is straightforward: an institution that already operates an enterprise platform should not acquire a second one alongside it.

Identity, document management, notifications, reference data, task workflow, integration and observability already exist and are already governed. Swift Lending OS consumes them and contributes what they do not have — the credit kernel and the lending domain.

Channels, solved

The UI runtime compiles one codebase to web, iOS and Android — which also answers the open question of whether the borrower surface is responsive web or native apps.

Languages, solved

Multi-language including non-Latin scripts is presentation metadata — translation content, not engineering effort.

Per-client deployment, solved

The platform's solution layer is exactly the per-client, configuration-only release model the lending programme needs for each estate and market.

Integration

Host systems already speak this language

Where the host systems already share the platform's integration idioms, connecting lending to them is native rather than bespoke.

Wallet

The kernel onboards as an external service provider behind the wallet's integration layer, alongside the existing payment, QR and biller providers.

Remittance

New enterprise-integration routes expose origination and decisioning so a send-time credit offer can be made. Existing KYC, compliance and FX systems are reused.

Digital banking

Core-banking adapters for posting and settlement, with bank channels as origination surfaces. The interface is genuine discovery work.

Capital market

An event bridge over the margin platform's existing loan-event topics — adding covenant monitoring and regulatory reporting without touching execution systems.

Common technology gravity

The estates already standardise on the same container orchestration, event streaming, relational storage, caching, object storage and observability stack the kernel needs. Compatibility is a starting condition, not something to engineer.

Design considerations

Three things this deployment gets right deliberately

Running on a general-purpose platform requires three decisions that lending, specifically, cannot get wrong.

  1. The credit kernel keeps one transactional boundary

    A general platform's default — one database per service with saga between them — is right for most domains and wrong for a loan ledger. The credit vertical is sized to contain the whole ledger, and saga appears only at external edges. See the boundary diagram →

  2. Lending brings its own process semantics

    Lending is workflow-heavy — approval chains, maker-checker, collections treatment. The domain uses the platform's underlying workflow engine directly, with the business-process and decision-workflow split it needs, rather than waiting on a generic abstraction.

  3. The stack is delivered whole

    The lending domain is not abstracted away from the platform it runs on. Institutions receive a coherent stack — foundation plus lending domain — rather than a domain that pretends to be portable and carries an abstraction layer nobody asked for.

Proven before it is committed

Any deployment on an existing platform begins with a fit-spike: prove the ledger pattern under the platform's data model, prove the sub-two-second decisioning path under real connector fan-out, and confirm which shared services are production-grade for this workload.

That evidence is gathered before the architecture is frozen — converting the largest assumption into a measured result while it is still cheap to be wrong.

In short

Lending capability without a second platform

1 · The layering already fits

An enterprise platform expects business domains on top of it. Lending is one — and Swift Lending OS is shaped to be exactly that.

2 · No duplicated foundation

Identity, documents, notifications, tasks and integration stay governed once, in the place the institution already governs them.

3 · Effort goes where it differentiates

None of those ten services makes a lending product better. The credit kernel and the lending domain do.
