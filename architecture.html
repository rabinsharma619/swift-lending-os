System shape

Five planes, cleanly separated

The architecture is organised so that what changes fastest is furthest from what must never break.

Channel plane
Where borrowers and operators actually are — host platforms, partner systems, direct operator UI, borrower portal and the public API. Swappable without touching lending logic.
Edge plane
Per-channel adapters and the API gateway. Each host system gets its own adapter speaking its own idiom, so the core never learns a channel's quirks.
Core plane
The lending core: origination, products and offers, the servicing ledger, payments, collections, monitoring, communications and the admin/public API — over a shared kernel of entities and state machines, expression runtime, credit operations ledger, policy registry, work queue, scheduler, audit, outbox and statutory guardrails.
Extracted plane
Separately deployable where the workload demands it — the decisioning service (bursty, latency-critical), the document renderer (CPU-heavy), the connector hub (the egress boundary) and reporting/batch workers.
Data plane
Transactional primary with standby, a modelled reporting replica, an event bus, cache and object storage. Analyst queries never contend with origination latency.
Why a modular core rather than microservices everywhere

The correctness-critical parts of lending benefit enormously from in-process transactional consistency, and self-hosting customers must be able to run the platform without a large platform-engineering practice. Module boundaries are enforced at build time, and the modules that genuinely need independent scaling are extractable from day one. Distributed transactions across loan balances is not a trade we make.

The load-bearing decision

The credit kernel is one transactional boundary

Balances, credit operations, schedules and allocation commit together — or not at all.

Saga at the external edges. Never inside the balance.

Eventual consistency between a payment and the balance it settles is precisely how lending platforms develop subtle, expensive, late-discovered defects. Everything that genuinely is distributed — payment rails, core-banking posting, a remittance leg — sits outside the boundary with compensating transactions.

Invariants

Six properties the architecture carries, and tests

Not aspirations. Each is enforced structurally, and each is testable.

Balances change only through credit operations

No service, adapter or batch job writes a balance column. They create operations that the calculation pipeline applies. Enforced by architecture tests.

Money is integer minor units

Every payload carries an integer amount and an ISO currency code. Floating point in a money path is a build failure, caught by static analysis.

Events publish only from the outbox

In the same database transaction as the state change they describe — so there are no phantom events and no lost ones.

Decisions are versioned and replayable

The decision of record is a deterministic policy artifact. Identical recorded inputs produce identical outputs, years later.

Statutory guardrails run outside policy scripts

A pricing script may propose any rate; the guardrail layer clamps or rejects it. Configuration error cannot breach a statutory cap.

Every topology runs the same artifacts

Including air-gapped. No capability exists that works only in a vendor-hosted deployment.

Open SDK and APIs

Extend without lock-in

Extension points are interfaces. The platform never requires subclassing a concrete platform class, and customer code lives in its own module and repository.

An upgrade is a dependency bump and a CI run — not a merge conflict against customisation. Semantic versioning with a published deprecation policy makes that a commitment rather than a hope.

Four connector shapes

Every integration — bureau, core banking, payment rail, KYC, AML, e-signature, accounting — composes from exactly four interface shapes, so a new provider is a small, well-understood piece of work rather than a project.

// Pull data about a subject. interface OutboundDataSource<S, T> { ConnectorDescriptor descriptor(); T fetch(S subject, FetchContext ctx); } // Cause an external effect: payout, // posting, SMS, envelope create. // MUST be idempotent on the key. interface OutboundCommand<C, R> { ConnectorDescriptor descriptor(); R execute(C command, CommandContext ctx); } // Plus: inbound webhook receivers // and scheduled import jobs.
Connector descriptor
Every connector declares auth, request and response schema, timeout, retry policy, circuit-breaker thresholds, cost model, PII classification per field and cache policy. The descriptor is what makes the rest automatic.
Call trace persistence
Every external call records request, response, latency, cost and outcome — attributable to a subject, a workflow execution and a policy version. This is what makes decision replay possible without re-calling a paid provider.
Failure handling
A typed failure taxonomy with a circuit-breaker state machine per provider. A degraded provider affects its own branch only — never the request pool.
Public API
REST with OpenAPI, OAuth 2.0, cursor pagination, RFC-standard problem details, mandatory idempotency keys on state-changing requests, and additive-only changes within a major version.
Sandbox
Every connector ships a fixture mode. No test suite requires a live vendor, and forced decline, timeout and failure scenarios are first-class fixtures.
Modular core

Two engines, one boundary between them

The separation that lets credit policy and journey shape evolve on different cadences, owned by different teams.

Business process

The state machine of an entity — which stages exist, which transitions are legal, what fires on transition, and what guards must hold. Declared as an artifact, reviewed like code.

Answers: what stage is this in, and what happens next?

Decision workflow

The algorithm invoked at a transition — fetch data, evaluate rules, return a verdict. Authored visually, versioned as an artifact, and it never blocks, waits or queues.

Answers: what is the verdict?

A workflow terminates by attaching facts — proceed, pause for human judgment, or hard stop — and exiting. The business process decides what those facts mean for the journey. Neither reaches into the other.

Decision artifacts, all first-class

Scorecards

Characteristic → attribute → points, with development support and per-programme variants.

Decision tables

Condition/outcome matrices with full execution trace.

Decision trees

Branching logic where the path itself is the explanation.

Expressions

One sandboxed runtime, multiple scopes — features, workflow logic, pricing, metrics.

Deploy anywhere

Your infrastructure, your rules

Four topologies from a developer laptop to a fully air-gapped institution — running the same artifacts, differing only in configuration.

TopologyShapeSuits
T1 — single node One command brings up the application, database, cache, object store, event bus and seeded data Development, demonstration, pilot. A new engineer is productive on day one
T2 — standard production Multi-zone orchestration, primary with synchronous standby, reporting replica, HA cache and bus The default for most institutions
T3 — high volume T2 plus aggressive autoscaling on the decisioning service, connector pool isolation, replica reads, partitioned batch Checkout-latency lending at scale
T4 — on-premise / air-gapped Mirrored registry, local object storage, no outbound dependency for runtime or licensing; signed offline update bundles Institutions that cannot accept hosted or connected deployment

Supply-chain integrity

Images signed and admission-verified, with software bills of materials attached as attestations and shipped inside the air-gap bundle for offline verification.

No downtime for minor releases

Rolling deployment with expand–migrate–contract schema changes. No big-bang cutovers.

Cloud-agnostic by construction

Containers and infrastructure-as-code, portable across major clouds and on-premise clusters alike.
