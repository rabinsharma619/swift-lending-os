Architecture

Organised so what changes fastest is furthest from what must never break

Client apps
Admin console, portals, widgets, mobile apps and the public API. No business logic lives in a channel.
Swift Intelligence · optional
A separate build-time service that drafts configuration through the same Admin API a person uses. Never in a request path; off in air-gapped installs.
Lending core
One deployable with build-time module boundaries. Credit, accounting and the kernel commit in one transaction — so a payment and its journal can never disagree.
Extracted services
Separately deployable where workload demands: decisioning is bursty and latency-critical, rendering is CPU-heavy.
Integration edge
The core banking port with certified drivers, and adapters for host platforms. Every distributed step has a compensating one.
Data
PostgreSQL with standby and a modelled reporting replica, an S3-compatible store, and optional bus, cache and search.

The load-bearing decision

Saga at the external edges. Never inside the balance.

Eventual consistency between a payment and the balance it settles is precisely how lending platforms develop subtle, expensive, late-discovered defects.

A general platform's default — one database per service with saga between them — is right for most domains and wrong for a loan ledger. The boundary is sized to contain the whole ledger and its accounting journals; everything genuinely distributed — rails, the remittance leg, core banking posting, commodity trades — sits outside it with compensating transactions.

Six invariants the architecture carries — and tests

Not aspirations. Each is enforced structurally, and each is testable.

  1. 01

    Balances change only through credit operations

    No service, adapter or batch job writes a balance column. Enforced by architecture tests.

  2. 02

    Money is integer minor units

    Floating point in a money path is a build failure, caught by static analysis.

  3. 03

    Events publish only from the outbox

    In the same transaction as the state change — no phantom events, none lost.

  4. 04

    Decisions are versioned and replayable

    Identical recorded inputs produce identical outputs, years later.

  5. 05

    Guardrails run outside policy scripts

    A script may propose any rate; the guardrail layer clamps or rejects it.

  6. 06

    Every topology runs the same artifacts

    Including air-gapped. No capability works only in a hosted deployment.

Open SDK — extend without lock-in

Extension points are interfaces. The platform never requires subclassing a concrete platform class, and each deployment's extensions live in their own module, built and maintained by Swift. An upgrade is a dependency bump and a CI run — not a merge conflict against customisation.

Every integration — bureau, core banking, payment rail, KYC, AML, e-signature, accounting — composes from exactly four interface shapes, so a new provider is a small, well-understood piece of work rather than a project.

Descriptor
Auth, schemas, timeout, retry, circuit breaker, cost model, PII class, cache policy
Call trace
Request, response, latency, cost and outcome — attributable to subject and policy version
Failure model
Typed taxonomy with a per-provider breaker; a degraded provider affects its branch only
Public API
OpenAPI, OAuth 2.0, cursor pagination, mandatory idempotency keys, additive-only within a major version
Sandbox
Fixture mode per connector — forced decline, timeout and failure are first-class

Two engines, one boundary between them

Business process

The state machine of an entity — which stages exist, which transitions are legal, what fires, what guards must hold. Declared as an artifact, reviewed like code.

Answers: what stage is this in, and what happens next?

Decision workflow

The algorithm invoked at a transition — fetch data, evaluate rules, return a verdict. It never blocks, waits or queues; it emits facts and exits.

Answers: what is the verdict?
